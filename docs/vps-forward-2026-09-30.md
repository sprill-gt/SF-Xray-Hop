## 正式服务与独立设备

以下检查使用原有节点凭据和正式服务，管理脚本为0.2.1；没有重装、交换用途或运行VPS本机压力测速。每个测试阶段先核对入口下游地址和身份确实对应诺亚、诺亚无下游，再执行操作。

| 场景 | 实际结果 |
|---|---|
| Windows VMISS Direct | 完整HTTPS成功，实际出口匹配VMISS基准 |
| Windows VMISS Relay | 完整HTTPS成功，实际出口匹配诺亚基准 |
| 停止诺亚Xray | VMISS Relay失败，Direct继续从VMISS出口；入口状态、配置摘要和服务PID／启动时间不变 |
| 恢复诺亚Xray | 首次Windows Relay请求超时（curl28）；第二次通过，原客户端JSON不变。不承诺无缝恢复 |
| VMISS导入不可达出口 | 拒绝候选；现有状态／配置和服务进程保持，原Relay继续出网 |
| VMISS修改为无效SNI | 保留默认目标及全部状态／配置，不重启入口服务 |
| VMISS Pre → Stable | 当次GitHub正式频道候选26.3.27实际启动，Windows26.9.9客户端经VMISS → 诺亚26.9.9完整双跳成功；之后恢复26.9.9 Pre |
| VMISS验证不兼容候选 | 指定官方1.8.24，能力检查拒绝；没有切换核心、状态、频道或服务进程，原Relay继续出网 |
| 固定同一核心再重复安装 | VMISS固定26.9.9后再次install，pinned频道与原客户端JSON保持；服务PID／启动时间不变，Windows双跳通过 |

停服测试设置了90秒自动恢复保护，并在正常恢复后撤销该临时任务。故障恢复的首次失败如实保留。Stable通过仅代表这次候选与现有配置／客户端组合，不是未来所有Stable都兼容的承诺。

官方来源：[Xray Releases](https://github.com/XTLS/Xray-core/releases)、[26.3.27](https://github.com/XTLS/Xray-core/releases/tag/v26.3.27)、[1.8.24](https://github.com/XTLS/Xray-core/releases/tag/v1.8.24)，核对日期2026-09-30。最终日常使用仍保留Pre频道。

独立Windows测试客户端使用Xray26.9.9、curl8.21.0，在任何脚本切换前发起一个HTTPS下载，经VMISS → 诺亚请求75000000字节，主动限速300000字节／秒、最长300秒。在该请求进行期间完成两台更新及入口脚本回滚／再更新，没有重新启动客户端或重试下载。实际HTTP200、`application/octet-stream`、curl退出0、完整接收75000000字节，耗时251.071秒，curl重试次数0。之后新建Direct、Relay请求仍分别匹配VMISS、诺亚基准出口。

**此项只证明本次脚本更新期间已有下载保持，不是吞吐或长期稳定性测量，也不承诺核心／路由变更无缝切换。** 用户报告约18 MB/s仍单独作为用户观察保留，不能与主动限速结果比较。

准备上述请求时，一个不同大小的公网源请求返回403，未进入更新检查；临时回环接收器被26.9.9默认私网访问限制阻止，也未计为通过。没有为测试修改生产freedom规则或增加公网端口。该限制的官方源码依据见[freedom.go](https://github.com/XTLS/Xray-core/blob/v26.9.9/proxy/freedom/freedom.go)，适用26.9.9，核对日期2026-09-30；隔离协议实验的专用放行与生产配置区别见[协议说明](protocol.md)。

## 最终诊断与清理

两台最终均为管理脚本0.2.2、Xray26.9.9、Pre频道、0-RTT、Chrome、XHTTP auto、`archive.archlinux.org`。将VMISS测试用pinned改回Pre后，两台完整状态分别与本轮开始前一致；VMISS仍为中转，诺亚仍为落地。
