# SF-Xray-Hop 正式版：产品定位与交互需求（R2 整合版）

状态：供本地 Agent 实施的需求整理，不代表这些功能已经实现或上一轮审查问题已经修复。
范围：在现有项目上增量调整，不重写代理数据面，不扩展成服务器管理平台。
修订：R2 整合脚本自身更新、自定义节点名、Xray 正式版切换/回滚，以及“省心使用前沿技术”的产品原则；有冲突时以本整合版替代 R1。上一轮安全审查与未完成验收仍然有效。
边界：这是需求文档更新，不是仓库代码补丁；未据此宣布任何新增功能已完成或已验收。

## 1. 产品定位：前沿默认，省心使用

**SF-Xray-Hop 是一个让用户省心使用 Xray 前沿加密与流量伪装能力的轻量脚本：默认一键直连，需要时快速搭建双机链式代理。**

- 默认路径：设备 ↔ 当前 VPS ↔ Internet。
- 可选链式：设备 ↔ 入口/中转 A ↔ 出口/落地 B ↔ Internet。
- 没有链式需求也能完整、独立使用，不必先了解双机架构。
- 当前采用已讨论的 VLESS Encryption + XHTTP + REALITY + xtls-rprx-vision 组合，保留 XHTTP auto、Chrome 指纹、0-RTT 默认与手动调整能力，其余采用已验证的 core 默认行为。
- 核心默认跟随官方 Pre；用户可以切换到兼容的正式发行版，或回滚/锁定已知可用版本。此能力不改变前沿优先的默认定位。
- 管理脚本自身默认安装项目正式发行版；稳定的安装/更新管理流程与前沿核心并不矛盾。
- 本项目降低使用新技术的配置与维护成本，不自创密码学、不默认堆叠所有上游可选功能。
- 对外强调“前沿优先、一键部署、快速链式、可回退”，不宣称“绝对最强、无法识别、零风险”。Pre 是发行类别，不代表每次发布都有新算法或更高安全强度。

对外介绍可用：

> 默认跟进 Xray 前沿加密与伪装能力，一键直连、快速链式；预发布优先，正式版可选，更新失败可回退。

这份需求替代此前安装时必选 RTT、先选角色、初始固定安装 26.9.9、默认展示两条用途不明确链接的交互。26.9.9 保留为历史验证基线，而不是永久安装版本。

“自动吃到前沿能力”的边界：

1. 已兼容的核心实现修复、指纹实现更新及传输优化：通过升级核心获得，不要求手工重配。
2. 项目需要适配的新配置字段/格式：通过脚本升级提供兼容层与测试，不靠猜测解析未知参数。
3. 需要两端同步的新握手方式或长期凭据：单独明确提示、验证和迁移，不能在普通升级时只改服务器并使已有客户端失效。

不要因为出现一个新算法名，就在每次升级时重新运行生成器覆盖现有 encryption/decryption。首次初始化与明确轮换可以生成新密钥，常规更新必须保留身份。

## 2. 保留的底层架构

一个正式 Xray 服务、一个公网 VLESS inbound、两个独立 UUID/email。

- Direct 身份：始终经本机 freedom 出口。
- Relay 身份：入口 A 配有下游时经下游；出口 B 无下游时经本机 freedom。
- 独立身份不要求第二个端口、第二个服务或另一套 REALITY 监听。
- 同一 inbound 的 REALITY/SNI/XHTTP path/服务端 VLESS Encryption 配置仍可共享。
- A、B 之间不共享服务器私钥；A 只导入连接 B 所需的客户端参数。
- 已配置下游但其故障时，A Relay 必须失败，不能自动改为 A 本机出口；A Direct 不受此路由策略影响。

可以继续在初始化时内部生成两种身份，但默认只向用户展示 Direct。隐藏未启用链式的链接不等于新增一套服务。

## 3. 首次安装：正常流程不询问协议参数

正常路径：

环境检查 → 获取最新官方 Pre → 下载校验 → 使用默认参数生成配置 → 候选配置与协议检查 → 启动正式服务 → 直连验证 → 展示直连链接。

默认值：

| 项目 | 需求 |
|---|---|
| Core 频道 | pre，选择最新已发布、非 draft 的官方 Pre-release |
| 版本选择 | 通过 releases 列表分页、明确过滤、按可解析版本比较；不能用字符串字典序或直接假设第一项正确 |
| 安装一致性 | 一次操作先解析并锁定 release/tag/资产，再下载同一版本；不在中途重新解析 latest |
| 监听端口 | 443 |
| REALITY 目标 | 沿用项目默认 archive.archlinux.org:443 |
| SNI | archive.archlinux.org，须通过实际目标兼容检查 |
| RTT | 默认允许 0-RTT 会话恢复，导出客户端默认 0rtt |
| XHTTP | auto |
| 指纹 | chrome |
| 本机角色 | 独立节点，未启用链式 |
| 节点名称 | 未命名时用 node-<稳定短标识>；不推断地区、商家、线路等级或 IP 类型；安装后可改为用户自定义名称 |

说明：GitHub /releases/latest 的定义排除 Pre，不能用它实现“最新 Pre”。正式版切换与版本回滚放在主菜单 2 的核心管理中；指定/锁定版本放其高级选项，不放首次正常安装问答里。

正常安装不询问 SNI、0/1-RTT、XMUX、padding、Chrome/Firefox、stream-one 等。异常时允许最少必要交互：443 被占用、已有非本项目 Xray、默认目标不可用、下载/校验失败、无法确定可达地址。

- 不自动杀掉占用 443 的服务，不覆盖其他脚本管理的 Xray。
- 默认目标失败时停止应用候选配置，提供重试或修正 SNI 的入口；不能报“安装成功”或静默使用一个未经验证的随机目标。
- 最新 Pre 不兼容时，不偷偷关闭 Encryption/Vision，也不谎称安装了最新版本。
- 不在更新时重新生成 UUID、长期密钥、shortId 或 XHTTP path。
- 重复安装保持身份、当前角色、自定义名称与核心频道；不能把已配置 A/B 重新初始化为独立节点，也不能把手动选择的 stable/pinned 重置为 pre。
- 交互终端在安装成功后展示一次直连链接；普通日志不写完整链接。无终端执行不应把凭据泄露进流水线日志。

成功页：

```text
安装完成
本机：node-a1b2c3
角色：独立节点
直连：设备 → node-a1b2c3 → Internet
名称：直连 | node-a1b2c3
[此处展示直连 VLESS 链接]

可选：修改本机名称；跳过不影响使用。
需要双机链式代理：运行 sfxh，选择 1。
```

“直连”指设备直接连接这一台代理服务器，不是设备绕过代理。

首次正常流程不增加必答的命名问卷；成功页提供可跳过的改名操作，之后可在菜单 5 修改。命令行非交互安装可传入经校验的名称。

## 5. 三种角色与链接用途

| 角色 | Direct 链接 | 菜单 4 | 额外说明 |
|---|---|---|---|
| 独立节点 | 展示本机直连 | 提示未启用链式，可进入引导 | 不把未配置下游的 Relay 包装为已完成链式 |
| 入口 A | 展示设备→A | 展示设备→A→B 的链式链接 | 必须有完整且已应用的下游配置 |
| 出口 B | 展示设备→B | 告知设备链接在入口 A，显示已登记入口地址 | 对接链接放在链式引导/出口管理里 |

对接链接仍是标准 VLESS URI，不是管理 token，也不是服务器私钥。
“B 对接链接”和“A 设备链式链接”可能使用同一种 URI 格式，但面向用户的用途与名称必须不同。

角色约束：

- 不能单凭“没有 nextHop”把独立节点自动标成出口 B。
- A 由成功应用下游配置产生；B 是用户在向导中明确选择的无下游出口模式。
- A 的下游暂时离线时，仍是 A，只是链路失败。
- 角色切换与运行配置必须校验一致，不能只改一个文字标签。
- v1 不自动支持“同时作为中间节点又作为其他链路出口”等多重角色 UI。

## 6. 链式引导

### 6.1 首选顺序：先 B，后 A

入口界面只问：

```text
这台机器在链路中的用途？
1. 入口 / 中转 A（设备首先连接的机器）
2. 出口 / 落地 B（最终对外访问的机器）
0. 返回
```

B 分支：

1. 确认无 nextHop；若原来是 A，先走明确的角色切换确认。
2. 保留 Direct 与现有接入密钥。
3. 显示“对接 | NOV-IPS”链接，说明“复制到 A 的链式引导，不是设备用的完整链式链接”。
4. 可选登记入口 A 的管理地址/IP和备注，回车可跳过。
5. 没有来自 A 的完整链路验证时，显示“出口已配置，等待 A 对接”，不能显示“完整链路已通过”。

A 分支：

1. 提示粘贴 B 的对接链接，隐藏输入并脱敏日志。
2. 安全解析、严格校验，并显示不包含秘密的摘要：B 名称、地址、端口、协议、RTT。
3. B 名称优先采用经过清理的备注，不依赖在线 IP 地理数据库。
4. 先测试候选下游与候选完整路径，确认后事务应用，失败恢复原状态。
5. 仍保留 A Direct。
6. 成功后显示唯一面向设备的链式链接“链式 | VMISS-CN2GIA→NOV-IPS”。
7. 显示本机 A 地址，方便用户在 B 登记；v1 不增加自动回传管理通道。

### 6.2 B 如何显示 A 的地址

仅凭“B 把分享链接交给 A”这一步，B 不会得到 A 的设备链接和管理资料。

v1 采用最小实现：用户登记入口地址，或之后在菜单 5 编辑。显示时标明来源为用户登记。

- 未登记：显示“入口地址未登记，请前往配置过 B 链接的入口机器”。
- 已登记：显示“入口 A：<地址>，请在该机菜单 4 获取设备链式链接”。
- 不能把日志里随便一个来源 IP、NAT 地址、访问过 B Direct 的 IP认定成 A 管理地址。
- 不扫网、不读取 SSH 密钥、不新增常驻管理 API，不伪造 A 链接。
- A 未成功对接前，即使 B 记录了 A 地址，也不能标记为已完成绑定。

### 6.3 替换、移除和切换角色

- 替换 B：测试 B2 成功才切换，保留 A 的设备地址、UUID等接入参数。
- B 故障：不自动直出；A Direct 可供用户主动切换。
- 主动移除下游/从 A 切换角色：明确显示旧链式身份将恢复本机出口这一影响，用户确认后才执行，沿用此前显式移除的产品语义。
- 移除或改角色后隐藏旧的“链式”导出名称，不能仍显示设备→A→B。
- 不在本地假称已经删除或修改另一台机器上的凭据/关联记录。

## 7. 自定义节点名称与链接命名

### 7.1 名称由用户定义，不推断线路质量

每台机器拥有独立、持久化、可编辑的显示名称。例如用户可以设置：

```text
A：VMISS-CN2GIA
B：NOV-IPS
```

名称是用户备注，不是项目验证的商家、线路或 IP 属性；不从 IP、ASN、地理数据库、角色或主机名推断 CN2GIA/住宅/纯净/高速等标签，不自动纠正用户的拼写与大小写。

未命名默认 `node-<稳定短标识>`。首次安装完成后可跳过改名；以后在菜单 5 修改。不为了改名修改系统 hostname。

### 7.2 展示规则

```text
直连 | <本机名>
链式 | <入口名>→<出口名>
对接 | <落地名>
```

按用户示例：

```text
直连 | VMISS-CN2GIA
直连 | NOV-IPS
链式 | VMISS-CN2GIA→NOV-IPS
对接 | NOV-IPS
```

箭头只表示入口→出口，不表示测速或线路评级。不默认加入完整协议栈、核心版本、RTT、整串 IP 或旗帜。终端列宽不足时可以显示省略，但不破坏完整保存的名称和导出的 URI。

### 7.3 名称与身份解耦

尽量复用既有状态模型，逻辑上区分：稳定内部节点标识、本机显示名称、下游连接参数、下游本地备注。不能把用户名称直接作为 UUID、email/routing tag、服务名、文件路径或 shell 命令。

改名只更新状态、展示与新导出链接的备注：

- 不修改 UUID、REALITY/VLESS Encryption 长期凭据、shortId、path、端口、角色或路由；
- 不重启 Xray，不打断已建立连接；
- 更新脚本、更新核心、切换频道、重复安装都保留自定义名称；
- 不把显示名称映射到 `xray uuid -i`，以免以后改名顺带改变身份。

### 7.4 下游名称来源

A 导入 B 链接时，从经过校验的 URI 备注读取建议名称；对于本项目格式只剥离已知用途前缀，不从任意文本猜 IP 或拓扑。摘要页允许修改为 A 本地更容易识别的备注。

B 改名后，A 已保存的名字不会自动更新：A 可以手动编辑本地备注，或重新导入 B 的新链接；重新导入时若连接参数完全没变，只更新备注，不重启。客户端已导入的旧节点名称同理，需要手动改名或重新导入，不会自动刷新。

不为同步名称增加订阅平台、公网 API 或跨机 SSH 信任。用户手动设置的本地备注应优先保留，替换下游时展示目标摘要供确认。

### 7.5 安全与编码

名称允许合理范围的中文、字母、数字、空格、连字符等普通显示字符，设置统一长度/字节上限。控制字符、ANSI 转义、换行和双向控制等不可见控制字符必须拒绝或清理后明确提示；不能直接拼入 shell、路径、JSON 或终端格式串。

URI fragment 只作为备注，执行正确的 UTF-8 与百分号编码/解码 round-trip。`$()`、引号等输入不得被执行；同名节点可以在确认页结合真实地址区分，不能靠名字判断为同一台机器。

## 8. 0-RTT 默认及调整范围

### 8.1 技术依据与安全边界

VLESS Encryption 的 0-RTT 是会话票据恢复，不是关闭加密，不是 TCP/REALITY/XHTTP 整条链零往返。
首次连接、票据无效等场景仍需正常密钥协商；服务端可限制或禁用票据。

官方设计包含票据生命周期和防重放记录。已查看的 v26.9.9 server.go 在恢复路径检查 ticket，并通过 NfsKeys.LoadOrStore 拒绝重复密钥，返回 replay detected；无效票据被拒绝。

因此不应把“0-RTT”一概判断为可被直接重放，但也不能把源码中存在防护等同完整安全证明或无法被识别。会话恢复仍涉及跨连接复用的密钥材料与生命周期取舍。这里不承诺每个未来 Pre 都保留同样行为。

### 8.2 默认行为

- 新安装默认允许恢复，客户端导出 0rtt。
- 服务端票据保持 core 已验证的有限时长；若模板必须给值，沿用已验证生成器的值，不能为了省 RTT无限延长。26.9.9 文档示例为600s，实际为随机300–600s。
- 调用 core 工具只用于需要生成密钥的首次初始化/明确轮换，切换 RTT 不生成新身份或长期密钥。
- 未认识的参数格式停止操作，不拼凑或猜测。
- 不自动把外部导入链接里明确指定的 1rtt 改为 0rtt；先按导入参数工作，另由用户修改下游设置。

### 8.3 菜单 7

普通节点/B：显示本机接入策略。
A：显示本机接入策略和当前 A→B 出站策略，分别修改。

- 本机接入：服务端是否允许票据恢复，以及新导出给设备/上游的客户端配置。
- A→B：本机持有的 nextHop 客户端 encryption 模式，服务端实际是否允许由 B 决定。

服务端 decryption 的票据时长与客户端 encryption 的0rtt/1rtt不是同一个字段，不能全文件替换。
本机设置变化不等于手机/另一台VPS的旧配置已同步；提示具体应更新哪些链接。
切换到1-RTT时，若产品含义是“本机接入禁止恢复”，必须在服务端落实限制，而不是仅改变新链接备注。
仅修改客户端导出且运行配置不变时不重启；实际服务端策略或出站改变时走原有事务。

## 9. SNI 修改

菜单6显示当前目标与SNI，允许输入新域名。

正常默认配置无需手动选择；手动修改时需要验证目标TLS能力、证书名称与REALITY所需配置一致性。
REALITY客户端的serverName需要被服务端serverNames允许，并与目标实际支持的名称兼容。

实施顺序：

新目标检查 → 生成候选 target/serverNames/导出 SNI → 协议验证 → 提示影响范围 → 确认后事务应用。

- 修改 A：影响设备→A；提示设备重新导入 A 链接。
- 修改 B：影响设备直连 B 以及 A→B；提示去 A 更新下游对接链接。
- 不承诺旧 SNI 永久继续有效。
- 不因修改 SNI 重生成 UUID、REALITY私钥、VLESS Encryption长期密钥。
- 核心更新、查看面板、角色状态刷新不自动修改 SNI。
- 当前单入站下不能声称只改了其中一个身份的SNI而不影响另一个。

## 10. 两套更新体系与前沿能力迁移

### 10.1 明确分开三个概念，不新增复杂管理平台

- **脚本版本**：SF-Xray-Hop 的安装器、菜单、URI 解析、配置生成、能力检测和修复。
- **核心版本/频道**：官方 Xray 二进制及 pre/stable/pinned 选择。
- **实际协议配置**：当前算法、身份、SNI、流控、传输与下游参数；不因版本号改变而盲目重建。

普通用户只需菜单 2 或 8，不需要自己编辑版本或协议文件。脚本可以有稳定的发行与恢复流程，同时默认使用前沿核心；不要求脚本自身也跟随未发布的 main。

### 10.2 Xray 核心管理（菜单 2）

```text
当前核心：<实际版本>
当前频道：Pre

1. 更新到当前频道最新版本
2. 切换频道：Pre / 正式版
3. 回滚到上一可用核心
4. 指定版本 / 锁定（高级）
0. 返回
```

频道规则：

| 频道 | 行为 |
|---|---|
| pre（默认） | 获取最新已发布、非 draft 的官方 Pre-release；不永久锁住历史基线 |
| stable | 获取上游标记为正式发行的目标版本，并验证当前配置实际兼容；不是脚本自己把某个 Pre 改名为 stable |
| pinned | 保持用户明确选择的确切版本；检查可以提示，但不擅自更新 |

GitHub Release 有独立的 draft/prerelease 字段；`/releases/latest` 排除 Pre。版本比较与候选发布状态必须正确处理，锁定本次操作的 tag/资产与校验值；不使用字符串字典序，不重新解析 latest 导致一次操作下载两个版本。

Pre 与正式版不是简单的新旧等价：切换正式版有可能降级，也可能不是。显示实际版本和变化方向。即使 pre 频道筛到的版本比当前版本旧，普通“检查/更新”也不得静默降级；降级必须明确确认。未来同版本由 Pre 转正式且二进制未变，可只更新频道元数据，无需重启。

最新 Pre 暂不兼容时保持现状并给出准确原因、更新脚本或选择其他版本的入口。不偷换旧版本后宣传“最新”；不要求每个新 Pre 都先进入人工白名单才能被测试与采用。

### 10.3 切换正式版与回滚的边界

切换目标核心前，保留现有配置测试：Encryption + XHTTP + REALITY + Vision、RTT、当前用户和路由、Direct、已有下游；验证失败不得替换活动核心。

- 目标正式版支持当前组合：允许事务切换，并持久化 core 频道为 stable。
- 目标不支持：明确指出缺少/不兼容的功能，保留原核心；可回滚到已知可用版本，不能静默关闭 Encryption/Vision、换 RAW 或重生成密钥来凑成功。
- 切换失败时，连频道选择一起恢复；不能核心仍是 Pre 却显示 stable 已切换成功。
- 主动回滚到历史版本后，默认锁定该版本并说明如何重回 pre/stable，防止下一次更新立即跳回刚回滚的版本。
- 自动失败恢复只恢复本次事务的 core/config/state/频道；记录失败候选与原因，不自动循环重试。
- 切换正式版不回滚脚本；回滚脚本也不能默认切换核心。
- 更新一台机器不等于另一台已更新，也不等于设备端核心已更新。不要在没有对端信息时承诺兼容所有旧客户端。

### 10.4 核心更新执行流程

解析并锁定版本 → 下载到临时位置并验证来源/摘要 → 完整归档发布 → 使用候选核心检查现有配置与实际协议 → 备份当前 binary/config/state → 事务切换 → 检查 Direct 与 Relay/下游及实际出口 → 成功提交或自动恢复。

保留上一轮审查要求：可重试的完整归档、低权限探测、出口判定、不完整目录自愈、失败回滚。同版本、同内容、同配置不重启；相同 tag 出现不同摘要不能当成正常无变化或无条件覆盖，须明确提示。

不后台定时升级，不打开菜单就安装或重启。不要用外部检测站一次失败直接断定核心损坏，区分不可达、握手失败、目标故障和出口不符。

### 10.5 脚本自身更新（菜单 8，正式版必需项）

```text
当前脚本：<实际版本 / commit>
目标脚本：<已解析的发行版本 / commit>
Xray 核心：<实际版本>（本次不更新）
核心频道：<当前策略>（保持）

1. 更新脚本到最新正式发行版
2. 回退上一个可恢复的脚本版本
0. 返回
```

优先追踪本项目正式发布的 Release/固定 commit，不直接覆盖为不断变化的 main。正式发布之前若没有正式发行包，应明确提示；维护者测试入口可以使用明确指定且可校验的预发行包，不得假装成正式发行。

脚本更新不仅覆盖一个启动文件，还须覆盖受管理的模块、模板和相应迁移文件，所有文件来自同一发行版本。UI 展示实际脚本版本，而不是读取远端 version 后假称本机已经更新。

最低流程：

下载固定发行包到临时目录 → 验证可信发布来源、完整性和安全解包 → 检查权限/依赖/状态格式兼容 → 备份本次将改动的脚本与状态 → 在临时副本上自检/迁移验证 → 原子发布整套版本 → 新版本自检 → 成功后重新进入菜单；失败恢复旧脚本与本次更改的状态。

安全和可维护性约束：

- 不用 `curl | bash` 作为本体更新器，不在可信性未验证前执行下载内容。
- 采用固定版本清单和发行包验证；清单与包来自同一被替换来源的单一摘要不能被描述为独立抗供应链入侵保障。发布者如提供签名，验证信任根不能同时从未验证的包内获取。
- 使用版本化脚本目录或等价整包原子切换，不能逐个覆盖正在执行的 lib 文件；单次命令固定自己的代码根目录，切换后再 exec 新菜单，避免新旧函数混用。
- 与安装/核心更新/卸载共享变更互斥；不能并发写状态。
- 状态格式迁移在副本上验证；失败恢复仅限本次事务，不能用任意旧状态覆盖用户后来新增的机器/凭据。
- 手动回退脚本必须检查当前状态和当前核心是否可由旧脚本管理；不兼容时拒绝破坏性回退，不默默恢复过期下游或旧密钥。
- 同版本无改动直接返回；脚本升级不自动调用首次初始化、不轮换身份、不清空下游、不重设 RTT/SNI/名称或 core 频道。
- 运行配置和核心不变时，不重启 Xray。管理脚本自检失败不应主动停止原本正常运行的代理。
- 若新脚本确实要求新的核心/配置，显示依赖与影响，另行确认；不能夹带无提示的核心升级。普通核心更新如先需要脚本更新，同样先说明。
- 记录本机实际脚本版本、commit/发行标识和包摘要，保留至少一个可恢复版本；不要无限归档占满磁盘。

建议命令语义（待实现，不代表当前已有）：

```text
sfxh self check
sfxh self update
sfxh self rollback
```

可沿用项目更合适的现有命名，但菜单必须明确“更新脚本”和“更新核心”是两个操作。

### 10.6 如何省心跟进真正的新能力

升级核心可以自动获得不需要改变两端配置的实现更新；脚本负责保持导入、生成、检查与更新流程兼容。当前配置字段中的握手/外观等匹配条件，仍须两端一致，不能假定下载新核心会把旧链接自动迁移为另一种算法。

新能力的处理原则：

| 变化 | 处理方式 |
|---|---|
| 保持当前配置兼容的核心修复/实现优化 | 核心更新后验证，用户无需重配 |
| 新版 core 的可兼容字段变化 | 脚本适配、候选测试；保留身份和已选默认策略 |
| 需要设备/A/B协调的新协议或长期密钥 | 单独显示收益、影响与同步范围，确认后受控迁移；不夹带在普通更新中 |
| 未识别格式/无法证明兼容 | 保持现状并提示；不猜参数、不宣传新能力已启用 |

不为这次需求增加协议商店或全新的第三套版本管理 UI。新算法出现时再基于官方实现和真实兼容测试定义迁移，不能预先把所有未知功能设为自动打开。

产品承诺是“尽量减少采用前沿能力的操作成本”，不是“任何新特性无论兼容性都强制启用”。

## 12. 实施优先级与验收

先完成上一轮安全审查修复并验证，再调整交互；不能只因菜单变漂亮就移除实验标记。

在既有代码基础上增量实现：

1. 默认安装与身份保持；
2. 三种角色和链接用途映射；
3. 链式向导、入口地址登记、自定义命名与身份解耦；

5. 脚本自身更新/恢复、核心pre/stable/pinned与回滚、卸载归属清单；
6. 在实际平台与客户端验收，包括脚本更新与核心换频道的组合失败路径。

最低验收表：

| 场景 | 必须结果 |

| 重复安装/核心升级 | 身份、SNI、名称、用户所选频道、Direct/Relay语义保持 |
| 独立节点菜单4 | 不显示伪装成链式的本机直出链接 |

| A导入B | 完整链式出口验证为预期B出口；A Direct仍为A |
| B停止 | A Relay失败；不自动从A出网；A Direct可用 |
| 替换B失败/成功 | 失败保留原链；成功后A设备连接参数保持 |

| RTT切换 | 0/1、冷连接/恢复/过期/重启均验证；不轮换长期凭据 |
| SNI修改 | 失败保留原配置；成功明确设备或上游同步范围 |
| 自定义名称 | VMISS-CN2GIA、NOV-IPS、中文等可持久化；不推断线路属性，不修改hostname/UUID/tag |
| 名称安全 | URI编码往返正确；控制字符/恶意shell输入不能注入；长名处理明确 |
| 修改备注/相同版本更新 | 不重启、不打断已有连接 |
| pre切换stable | 目标兼容才应用；成功保存stable；失败完整保留原核心、配置和频道 |
| 不兼容正式版 | 不静默删Encryption/Vision，不偷偷换协议，不显示切换成功 |
| 主动核心回滚 | 恢复已验证版本并明确锁定策略；脚本不自动跟着回退 |
| 已选stable/pinned再更新脚本或重复安装 | 不被重置为pre |
| 脚本升级 | 完整包同一版本，状态迁移正确，名称/密钥/下游/核心/频道保持 |
| 脚本更新中断/坏包/自检失败 | 旧脚本可恢复，既有代理保持，不留新旧混合代码 |
| 脚本历史版本回退 | 校验当前状态和核心兼容性；不恢复过时凭据覆盖后续修改 |
| 多操作并发 | 核心更新、脚本更新、配置修改、卸载不会相互写坏状态 |
| 卸载 | 项目资产清除，其他服务/SSH/共享依赖保留，无越界删除 |
| 正式发布 | 完成Debian12实际A/B、独立客户端、真实重启/恢复、外部200M压力及持续运行测试 |

测试未完成就写未完成。1C1G/200M是否有余量以外部客户端实测为准，不使用之前聊天中的示例CPU/吞吐数字作为验收证据。
