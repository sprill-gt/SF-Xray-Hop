# 设计说明

## 范围与已确认决策

R2 默认单机直连，按需启用设备→入口→出口的可靠双跳，目前验证边界见[验收记录](testing.md)。没有面板、Docker、数据库、SSH 信任、订阅、多出口策略或自动故障切换。参考 [233boy/Xray 的数字交互](https://github.com/233boy/Xray/blob/main/src/core.sh)，自行实现适用于本项目的模块，没有复制其脚本。

0.1.3 的一行安装与完成后引导参考 [233boy V2Ray 安装／管理流程](https://github.com/233boy/v2ray/wiki/V2Ray%E4%B8%80%E9%94%AE%E5%AE%89%E8%A3%85%E8%84%9A%E6%9C%AC)（2026-09-30核对）：远程一行入口、完成后明确下一步、短命令管理、菜单空回车退出。R2 将首次安装改为默认0-RTT、无协议问答；成功后仅在交互终端显示一次直连链接。安装入口独立下载完整源码、恢复管道下的终端输入、调用同一安装业务函数；临时源码不作为长期安装目录。

一个正式 xray.service、一个公网 VLESS inbound，默认 TCP 443。允许有超时和清理机制的临时本机探测进程。运行配置或核心变化允许短暂重连；单纯修改显示／导出设置不重启。

## 节点与身份

所有节点使用同一种状态结构。Direct 和 Relay 使用不同 UUID、固定 email，通过 inboundTag + user 分流。Direct 永远到 freedom；Relay 没有 Next-Hop 时到 freedom，有 Next-Hop 时只到该出口。下游失败不得隐式直出。末尾拒绝路由防止误匹配。

首个日常使用目标限定为单入口双跳。多个入口可以共用出口的 Relay 凭据，但没有逐入口独立授权、撤销或统计；`presentation.entry` 只是一个展示登记项，不是授权列表。不会将共享一个 UUID 描述为多用户隔离。

“1号入口／2号出口”仅是向导显示位置，不是协议节点类型。向导不声称知道另一台的管理状态。R2 的链式备注包含本机和本地下游别名；替换出口保持入口连接参数，允许更新备注。旧客户端备注不会自动同步。

## 模块与状态

交互层与业务层分离：平台、生成配置、URI、核心、target、探测、事务、更新、安装、向导和性能检测独立。菜单与命令调用同一业务函数。

状态schema2增加 presentation（用途、下游别名、用户登记的入口）；schema1可读，在下一次变更中复制转换。状态包含 schemaVersion、本机 endpoint、两种身份、Encryption 参数对、REALITY 设置、可选 nextHop、核心归档 ID。state 是唯一配置源。向导进度独立保存，不控制路由。未知 schema 和外部配置改动禁止静默覆盖。

| 模块 | 当前职责 |
|---|---|
| common / platform | 安全路径、锁、脱敏、系统和依赖检查 |
| model / templates/model.jq | 状态校验、单 inbound 双身份路由、客户端配置 |
| links / core / reality | 严格 URI、官方核心归档及能力适配、target 候选 |
| core-safety-worker / data/core-safety.json | 独立网络命名空间内的认证后私网防护检查，无生产凭据 |
| health / transaction | 临时协议进程、带时间的检测、代次提交与恢复 |
| install / operations | 安装、下游、RTT、更新回滚、卸载 |
| manager / self | 版本来源、发行验证、完整脚本原子更新与兼容回退 |
| product | 用途、名称及登记信息，与协议身份分离 |
| ui / benchmark | 中文数字流程和进度、有限时限的性能测试 |

配置布局：`/etc/sf-xray-hop/generations/<代次>/` 包含 `state.json`、`config.json`、`core-id`、`SHA256SUMS`。`active` 是唯一原子切换点；根目录的 `state.json`、`config.json` 通过它引用当前文件。`transaction.json` 保存旧／新代次和事务所有者，`guide.json` 保存当前流程用途、阶段、代次及时间，`backups/` 保存修改前副本。

核心位于 `/var/lib/sf-xray-hop/cores/<版本-散列前缀>/xray`，归档 metadata 记录官方 ZIP 与 binary 散列、来源和实际验证状态。缓存位于 `cache/`。管理程序安装到 `/usr/local/lib/sf-xray-hop/releases/<版本-内容摘要>/`，根入口为原子切换的符号链接。旧版普通文件入口升级前会保存完整旧代码；所有模块按入口的真实目录加载。

## 一致性

每次变更：排他锁→备份当前代次→候选状态和完整配置→语法与 core 检查→临时连接测试→原子活动指针→restart→正式测试→标记成功。失败恢复事务前完整代次并再次测试。

0.1.4 先比较状态、规范化配置和核心二进制摘要。状态完全一致且服务正在运行时直接返回；只有名称、导出指纹或频道等元数据变化时仍提交完整一致代次，但不重启或网络复测，检测缓存保留原时间。metadata 事务中断恢复也不重启。显式运行配置操作／保留配置恢复仍验证并启动服务；R2 的纯显示修改即使服务已停止也不会启动它。

核心先在同文件系统唯一 staging 中写入并校验、同步，再持有对应归档锁原子发布。未引用的损坏目录隔离重建；任何保留代次、备份或运行引用保护原归档。归档中断重试和引用安全清理独立于配置事务。

core 引用、config、state 属于同一不可变代次。事务记录区分正在执行的事务和进程死亡／重启遗留事务；启动准备程序恢复后再准备运行配置，避免锁死和混合版本。

PID 与 Linux 启动 ID、进程 starttime 一起核对，避免 PID 复用误判。启动准备程序遇到仍在执行的切换时使用候选代次；遇到失去所有者的记录时恢复旧代次。首次安装没有旧代次，失败则停止服务。并发修改通过排他锁和预期代次检查拒绝覆盖。临时进程有超时，且关闭继承的锁描述符。

0.1.1 在实机测试阶段补充恢复处理：探测子 shell 和 systemctl 客户端也关闭继承的锁，避免管理进程被终止后遗留子进程阻塞恢复；僵尸进程不算有效事务所有者。显式管理重启会清除 systemd 的启动限流计数，使候选连续启动失败后仍能恢复旧代次；服务自身的自动重启限制保持有效。

## 安全

持久配置和备份目录 700、文件 600；root 管理，专用服务用户运行 Xray。运行时配置按需复制。B 只向 A 提供客户端材料。输入不 eval，秘密不作为命令行参数传递，不写入自动输出或日志。保留备份即保留旧秘密，默认完整卸载删除私密备份，输入确认词后执行；仅 --keep-data 显式保留。

0.2.3增加行为门槛：核心下载归档、运行配置事务（含离线回滚）和doctor均检查候选是否仍阻断认证后的私网TCP请求。隔离不可用或结果未知即拒绝候选；具体覆盖、缓存与局限见[本轮审查](audit-0.2.2.md)。服务启动恢复沿用已提交代次，不在开机恢复时联网升级或静默换核心。

运行目录和日志公共父目录由 root 持有、0711，仅用于路径穿越，不可列出文件。私密运行配置属于 sfxray、0600；日志分成 root 的 `manager/` 和 sfxray 的 `core/`，子目录均为0700。服务用户不能替换 root 管理日志或准备程序的路径。核心 binary 和无秘密的父目录可读可执行。管理代码由 root 持有，禁止其他用户写入。

可用性边界：运行配置变更会重启正式服务，已有连接可能重连；没有自动故障切换。显式离线核心恢复只验证本地，不推进已验证代次。管理代码升级只接受相同运行配置及相同服务单元，不在脚本切换时迁移状态；下一次配置变更复制转换到schema2，旧脚本读不懂当前状态则拒绝回退。v1 不提供独立用户平台、隔离监听、多出口策略或完整拓扑证明。三系统的低端口能力及权限隔离仍需实机验收。
