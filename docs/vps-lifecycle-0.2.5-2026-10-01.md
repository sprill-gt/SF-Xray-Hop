两台均尝试应用官方 26.3.27，安全门槛拒绝候选，未发布至核心归档，正式配置和进程不变。随后实际应用 26.9.9、恢复 pre／26.9.30，再从真正成功使用过的历史归档 offline 回退到 26.9.9。回退前移走对应安全检查缓存，确认重新运行隔离检测，状态标为 `unverified-offline`；另外执行的在线 doctor／Windows 请求不冒充离线检查。最后恢复 pre／26.9.30，保留当时下游与身份材料。

事务故障通过正在运行的 RTT 修改命令产生：新代次已激活、尚未提交时终止独立进程组，再重启整台 VPS。两台 boot ID 均改变，原 state/config 摘要恢复、事务记录清除、服务 active/enabled，SSH 配置摘要保持。诺亚约 39.460 秒、VMISS 约 20.508 秒后观测到恢复，包含 SSH 重试及轮询，不是精确业务中断时间。没有把正常重启称为断电。

## 设备路由与失败保留

独立 Windows 官方 Xray 26.9.9（`52a412d`）使用服务器导出的客户端 JSON，通过回环 HTTP 代理请求同一 IPv4 出口端点；每个正常批次要求三个出口样本及一次额外 HTTPS 成功。Windows 核心 SHA256 为 `0d0fc0ea2b05641acb78c01fc36ad694e7b029861b2d5eb93da0e3e9fda9a98f`，与实际 v2rayN 所带核心逐字节相同。

| 场景 | 结果 |
|---|---|
| VMISS Direct 出 VMISS、Relay 出 诺亚，诺亚 Direct 基准 | 通过 |
| 不可达候选替换 | 拒绝候选，旧配置及真正 Xray 进程保持，原线路仍可请求 |
| 重新导入同一诺亚出口 | 通过，入口连接材料保持；不计作独立第三台 B2 |
| 主动取消／重新建立链式 | 已保存 Relay JSON 分别出 VMISS／诺亚，入口材料保持 |
| 停止诺亚 | Relay 失败，VMISS Direct 继续可用，没有自动直出 |
| 恢复诺亚 | 请求重试后恢复，未手工重启 VMISS |

生命周期阶段保留了五个正向批次的失败：诺亚三次核心切换后、出口停启后、整机重启后。新测试器记录到每次均为批内第一个 HTTPS 请求，curl 35，后续批次成功。由此可确认该现象在 Debian 13 仍存在，不能归因于 Ubuntu 22.04，也没有把重试成功统计成无中断。

## 常驻客户端的出口重启对比

每种下游 RTT 分别保留同一个 Windows 客户端进程，预热后重启诺亚三次。Device → VMISS 配置不变，只使用现有 `sfxh rtt downstream 0|1` 修改 VMISS → 诺亚偏好；每轮要求连续三个请求成功。VMISS 配置与真正 Xray 进程在各组三次重启期间保持。测试完成已恢复原 0-RTT 下游与入口材料。

| 下游 RTT | 三次重启后的失败请求数 | 原因码 | 首次成功观测时间 |
|---|---|---|---|
| 0-RTT | 1、2、1 | 三次 curl 28，另一次 curl 35 | 9.579、11.002、9.640 秒 |
| 1-RTT | 1、1、1 | 三次 curl 28 | 9.536、9.691、9.638 秒 |

时间从发起 SSH 重启命令计算，包含服务重启、请求和一秒采样间隔。curl 连接超时上限为五秒；这个结果不能表示网络 RTT，也不能表示 GUI 的恢复时间。六次均自动恢复，未重启 Windows 客户端或 VMISS；1-RTT 没有消除重启期间的首次超时，不能宣传为修复。

2026-10-01 核对的 26.9.30 [服务端源码](https://github.com/XTLS/Xray-core/blob/v26.9.30/proxy/vless/encryption/server.go) 在内存保存票据，遇到失效票据返回错误；[客户端读取实现](https://github.com/XTLS/Xray-core/blob/v26.9.30/proxy/vless/encryption/common.go) 会使旧票据到期并要求重新握手。这能说明一种可能的恢复路径，但本轮没有取得对应请求的内部错误证据，且 1-RTT 仍出现超时，尚不能把所有失败归结为票据问题。默认协议参数保持不变。

## 客户端与持续运行

实际 Windows GUI 为 v2rayN 7.25.2，产品版本 `7.25.2+28139853a8087d81e1ac7ffaf7013b937958f5d2`。通过剪贴板实际导入 Direct／Relay 两条长 URI，长度分别为 1924／1942 字符，Encryption 均为 1610 字符；除测试备注外不改链接参数。只读核对导入数据库中的地址、端口、UUID、完整 Encryption、flow、传输、安全、SNI、公钥、shortId、指纹、路径及 mode，13 项均与原链接一致。导入未改变原活动配置。

首次核对误读 v2rayN 旧数据库列，留下了一条测试器失败记录；使用当前 `Password`、`ProtoExtra`、`TransportExtra` 后两条均通过。它不是客户端丢字段的证据。原配置和数据库已做私密备份，未覆盖现有节点。

实际 GUI 的连接及 JSON 导入没有完成，用户已停止窗口操作；Android v2rayNG 2.3.8 没有可操作设备，本次未实际验证。首次持续测试在五次成功代理请求后因 SSH 资源采样超时中止，两台 Xray 没有重启；改进采样后重新开始的一轮，在用户要求暂停前完成十二次请求、零失败。两轮均未完成十分钟及空闲恢复窗口，不记为持续稳定性通过，也没有据此计算资源趋势。

暂停时已经结束 Windows 测试客户端和后台测试程序；两台 Xray／SSH 均 active，没有未完成配置或管理器事务，也没有所检查的残留探测单元。服务保持 0.2.5 管理器、26.9.30／pre、VMISS 有 Next-Hop、诺亚无 Next-Hop。私密测试现场与离机备份保留，未执行原定的最终全套复测和测试目录清理；不得将其写成已经完成。

## 支持及发布边界

当前仅声明 Debian 13、Ubuntu 24.04.3 LTS 的 amd64 支持。本文提供 Debian 13.3 入口 → Debian 13.7 出口的 0.2.5 证据；Ubuntu 24.04.3 的实机结果来自 [0.2.4 历史验收](vps-lifecycle-0.2.4-2026-10-01.md)，没有拿它充当 0.2.5 的部署证据。其他混合配对未测。

第三台独立 B2、真实断电、吞吐压力、手机 GUI 和长期日常趋势未测。用户随后确认停止追加重复故障测试，将客户端及日常体验验收接手，并同意进入 RC。维护重启时可恢复的短暂请求失败作为已知行为记录，不单独阻塞发布；持续断流、配置丢失、错误出口或不可恢复更新才属于阻塞问题。[当前 RC 交付与转正规则](release-candidate-0.2.6.md)。
